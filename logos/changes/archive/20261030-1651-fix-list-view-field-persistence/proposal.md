# 变更提案：修复列表视图字段编辑持久化

> module: core | created: 2026-10-30 | source: GitHub Issue #58

## 变更原因

在协作房间的列表视图中修改字段名、注释、主键、不为空、唯一、自增或类型后，输入控件显示了新值，但画布 Inspector 与服务端数据均未更新，`store.dirty` 也未按预期置位。用户会误以为批量整理字段已经保存，存在静默丢失工作的风险。

现有 `ST-SP-LIST-02` 在 Mock API / Mock 协作通道下通过，只能证明局部提交与模拟落账链路可用，不能覆盖 Issue 所示的真实服务端持久化与重新加载一致性。本次需以真实故障路径回归为依据，修复列表字段编辑到持久化之间的断点。

2026-10-30 实际验证结论：新增真实 backend + 真实 WebSocket 的全屏 ListView 回归后，字段名、注释、PK / NN / UNIQUE / 自增、类型与长度均成功物化到服务端，刷新重进房间后完整恢复，Viewer 只读拦截也通过。现行 `ListFieldRow` 提交、store watcher、op 上行与服务端物化链路无需业务代码修复；本提案收敛为真实持久化回归防护与 Issue #58 不可复现的关闭依据。

## 变更类型

代码级修复（既有行为未按规格工作，不引入新需求或接口契约）。

## 变更范围

- 影响的需求文档：无；`core-01-requirements.md` 的 US-04 / FR-07 已规定编辑自动保存
- 影响的功能规格：无；`core-04-side-panel-tabs.md` §10.5 已规定列表行内编辑与画布 / Inspector 同源同账
- 影响的业务场景：S01（编辑并保存图表）；协作房间内的 op 保存链路涉及 S05，但不改变 OT 协议
- 影响的部署方案：无
- 影响的 API：无契约变更；复用现有非房间 `PUT /api/v1/diagrams/{id}` 与房间 WS op 保存通路
- 影响的 DB 表：无 Schema 变更
- 影响的编排测试：无
- 影响的测试用例：强化既有 `ST-SP-LIST-02`，覆盖全屏 ListView、字段文本 / 约束 / 类型编辑、保存后重新加载及服务端快照一致性；复用 `ST-P-01` 的真实持久化验收语义
- 影响的 smoke 测试：无

- 是否涉及数据迁移：否
- 是否需要回滚预案：否
- 是否需要 smoke：否

## 变更概述

通过真实服务端回归确认并持续保障列表视图字段编辑从行内提交、store 脏标记到自动保存 / 协作 op 上行的完整链路。现行实现已满足字段名、注释、约束和类型编辑与画布 Inspector 等价，且 Viewer / 分享只读拦截有效，因此不修改业务代码。

新增针对 Issue #58 的回归测试：不仅断言控件值或 Mock 回调，还验证真实服务端快照与重新加载后的字段值一致，并接入 OpenLogos reporter。保持现有 API、数据库结构、交互规格和撤销行为不变。
