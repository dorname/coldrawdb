### P01：主流 ER 工具无法自托管

- **因为**：dbdiagram.io、QuickDBD、drawdb 等主流方案要么强制云端账号，要么仅客户端存储
- **导致**：用户的数据受制于第三方服务可用性与隐私政策
- **造成**：
  - 企业内网/离线环境无法部署
  - 隐私敏感场景（医疗、金融、政府）无法使用
  - 长期订阅成本不可控

→ **关联场景**：`S01`（编辑保存）+ `S02`（分享链接）—— 两者共同覆盖"自托管 + 跨设备访问"两大子痛点

### P02：客户端工具缺乏持久化后端

- **因为**：drawdb 等客户端方案仅靠 IndexedDB / Dexie 存储，无服务端
- **导致**：浏览器清理缓存即丢图；换设备/换浏览器需要重新导入；多端无法同步
- **造成**：
  - 重要设计资产反复重建（实际社区高频反馈 issue 关键词："lost diagram"、"browser cache cleared"）
  - 工作流在设备切换时断裂
  - 设计版本散落各处，无法追溯历史

→ **关联场景**：`S01`（自动保存到 SQLite 后端，PUT /api/v1/diagrams/{id}）

### P03：团队评审与协作成本高

- **因为**：现有工具不支持多人实时编辑、需手动 merge JSON / SQL 导出文件
- **导致**：评审需要互相发送文件；多人同时编辑会产生覆盖（无冲突感知）；缺乏审计记录
- **造成**：
  - 评审周期长（典型流程：导出 → 邮件 → 评论 → 修改 → 再次导出 → 循环）
  - 合规风险（设计变更无审计记录，金融/医疗场景尤其严重）
  - 沟通成本高（"你看了 v3 还是 v4？"）

→ **关联场景**：
- `S01` 提供 409 revision 冲突检测（V1 仅感知冲突，不解决实时协作）
- V2 计划新增 `S04`（房间管理）+ `S05`（OT 实时协作）

### P04：设计→真实数据库的迁移门槛高

- **因为**：现有工具的 SQL 导入导出能力不完整（DBML 弱、双向支持有限；不同引擎方言差异大）
- **导致**：设计→真实数据库需要手工修正；DB→设计反向无法还原关系/索引/枚举
- **造成**：
  - 上线流程慢（设计稿与实际 DDL 不一致时需反复对齐）
  - 易出语法错误（手工迁移时遗漏引号/类型映射）
  - 架构 review 与 DB schema 脱节（reviewer 看的是设计稿，DBA 看的是实际库）

→ **关联场景**：`S01 + 桥接层`
- `CAP-BRIDGE-01`：7 引擎 SQL 导出（MySQL / PG / SQLite / MariaDB / MSSQL / OracleSQL / Generic）
- `CAP-BRIDGE-02`：7 引擎 SQL 导入
- `CAP-BRIDGE-03`：DBML 双向
- `CAP-BRIDGE-04`：JSON 双向（`POST /api/v1/diagrams/import`）
