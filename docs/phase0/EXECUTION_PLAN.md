## 1. 最终目标定义（完成态）

当以下条件全部满足，视为目标达成：
1. diagram 主链路数据（table/field/reference/note/area/indice）以数据库为唯一真实来源。
2. 后端 API 具备 revision 乐观锁、事务一致性、导入历史数据能力。
3. Rust Web 前端可完成主流程编辑与保存加载，覆盖生产核心场景。
4. 灰度发布后指标达标，旧链路下线并保留回滚预案。

---

## 2. 执行原则（确保“按计划执行=获得产出”）

- **先冻结契约，再开发实现**：先 ERD/OpenAPI/迁移策略，后编码。
- **每阶段必须有可验证产物**：文档、脚本、接口、测试报告缺一不可。
- **每阶段必须有退出条件（DoD）**：未达 DoD 不进入下一阶段。
- **每阶段必须有回滚点**：保证问题出现时可控回退。

---

## 3. 分阶段执行清单（可直接照做）

## Phase 0：方案冻结（已完成，作为基线）

### 任务
1. 固化 ERD。
2. 固化 OpenAPI v1 草案。
3. 固化迁移策略文档。
4. 记录架构评审结论并回填文档。

### 产出
- `docs/phase0/ERD.md`
- `docs/phase0/openapi-v1-draft.yaml`

### DoD
- 三份文档评审通过。
- 评审决议（`is_deleted`、`updated_at`、reference 弱约束）已落盘。

---

## Phase 1：数据库落地（预计 2 周）

### 任务（按顺序）
1. 建立 migration 目录与版本脚本（up/down）。
2. 按 ERD 修正/新增字段：`revision`、`is_deleted`、`updated_at`。
3. 修复命名差异：`diagram_link.reference` -> `diagram_link.reference_id`。
4. 补齐索引：`diagram_link(diagram_id)`、`table_link(table_id)`、`indice_link(indice_id)`。
5. 实现 repository 层（diagram 全量读写 + 事务）。

### 产出
- `backend/migrations/*`
- schema 变更说明文档
- repository 代码与事务封装

### DoD
- 数据库可从空库迁移到最新版。
- 复杂 diagram（20+ tables / 200+ fields）可完整保存并读取。
- 保存失败可事务回滚，无脏数据。

### 回滚点
- down migration 可回退至 Phase 0 前 schema。

---

## Phase 2：API 完整化（预计 1~2 周）

### 任务（按顺序）
1. 落地接口：
   - `POST /api/v1/diagrams`
   - `GET /api/v1/diagrams/{id}`
   - `PUT /api/v1/diagrams/{id}`
   - `DELETE /api/v1/diagrams/{id}`
   - `POST /api/v1/diagrams/import`
2. 实现 revision 乐观锁：`expected_revision` 不匹配返回 `409`。
3. 统一错误码与响应结构（含 `request_id`）。
4. 增加 API 集成测试（成功路径 + 冲突 + 非法数据导入）。

### 产出
- API 控制器/服务层代码
- 集成测试报告
- OpenAPI 与实现一致性校验记录

### DoD
- 核心 API 全部可用，测试通过。
- 并发冲突稳定复现并返回 409。
- 导入接口具备容错与 warning 返回。

### 回滚点
- 通过配置开关禁用新 API，回退旧持久化路径。

---

## Phase 3：迁移桥接（旧前端接入新存储，预计 1 周）

### 任务（按顺序）
1. 旧前端增加“迁移到数据库”入口。
2. 增加读策略：数据库优先，失败回退本地读取。
3. 增加写策略：数据库优先（可限时双写本地，最长 4 周）。
4. 增加迁移日志与失败重试机制。

### 产出
- 迁移入口 UI
- 导入流程日志
- 双写开关与灰度配置

### DoD
- 历史本地数据可一键导入。
- 导入成功率 >= 99%。
- 导入失败可定位、可重试。

### 回滚点
- 关闭数据库写开关，恢复本地保存。

---

## Phase 4：Rust Web MVP（预计 3~4 周）

### 任务（按顺序）
1. 完成 Rust Web 技术选型 PoC（Leptos/Yew/Dioxus 三选一，评分决策）。
2. 落地 MVP 功能：建表、加字段、建关联、保存、加载。
3. 接入 API 与冲突提示（409 提示用户刷新/覆盖）。
4. 补齐基础体验：撤销重做、缩放平移、最小工具栏。

### 产出
- Rust Web MVP 工程
- PoC 评估结论文档
- 与后端联调报告

### DoD
- Rust Web 覆盖核心主流程（可替换旧前端主链路）。
- 首屏可交互与保存性能不劣于旧版 10% 以上。

### 回滚点
- 继续由旧前端承接生产流量，Rust Web 仅灰度。

---

## Phase 5：灰度切流与收尾（预计 2 周）

### 任务（按顺序）
1. 小流量灰度（5% -> 20% -> 50% -> 100%）。
2. 观察指标：保存成功率、P95、冲突率、导入失败率。
3. 异常触发自动回退策略。
4. 完成旧链路下线与文档归档。

### 产出
- 灰度发布记录
- 指标看板截图/报表
- 切流复盘与回滚手册

### DoD
- 保存成功率 >= 99.95%。
- `GET /diagrams/{id}` P95 < 300ms，`PUT` P95 < 500ms。
- 连续观察窗口内无严重一致性事故。

### 回滚点
- 任意阶段可回退至旧前端 + 本地保存模式（按开关控制）。

---

## 4. 执行节奏（建议）

- 周会：每周一次，检查阶段 DoD 达成情况。
- 日会：同步阻塞项（接口不一致、迁移失败样本、性能回退）。
- 门禁：未完成当前阶段 DoD，不允许推进下一阶段。

---

## 5. 角色分工（最小配置）

- 架构负责人（1）：把控 ERD/API/迁移策略一致性。
- 后端工程师（2）：migration + API + repository + 测试。
- 前端工程师（2）：桥接迁移 + Rust Web MVP。
- QA（1）：迁移回归、冲突场景、性能回归。
- SRE/运维（1）：灰度策略、监控告警、回滚演练。

---

## 6. 风险与卡点处理预案

1. **导入失败样本过多**：先扩展容错映射，再批处理修复脚本。
2. **409 冲突率高**：优化自动保存节流 + 合并策略。
3. **Rust Web 性能回退**：按模块定位（渲染/状态/网络）并分批优化。
4. **双轨维护过久**：设置截止日期，超期必须切流决策。
